# Phase 8: Verify Social Proof and Remove Questionable Claims

Audited every testimonial, endorsement, review, and media quotation on the site against the brief's requirements before changing anything. The headline finding: the fabricated press quotes the brief specifically names ("The Reading Room," "Literary Notes") had already been found and removed in an earlier phase of this engagement, before Phases 1–8 even began — confirmed from `src/data/press.ts`'s own history. The real, live gap was the brief's required `verified` field, which didn't exist in the schema at all.

## Checked, already compliant — no change needed

- **"The Reading Room" / "Literary Notes" fabricated press quotes.** Already removed. `src/data/press.ts` is an empty array today, with a code comment documenting exactly this: it previously held three fabricated quotes attributed to made-up outlets, which were found and deleted for violating the "do not fabricate reviews/media appearances" rule — the same rule this phase's brief restates. `PressStrip.tsx` renders nothing when the array is empty, so there's no placeholder or filler standing in for them.
- **"A storyteller unafraid to cross genres" / "One of the more versatile voices in contemporary Indian fiction."** Searched the entire codebase for both exact lines — neither exists anywhere today. Same history as above.
- **Heading wording.** `/testimonials` already uses the brief's exact required heading, "What Readers Are Saying." The homepage strip uses "What Readers Say" (equivalent, not the exaggerated alternatives the brief warns against). Neither "Readers Are Obsessed" nor "Everyone Is Talking About…" appears anywhere.
- **No-review fallback.** `BookDetail.tsx`'s reviews section (`book.testimonials && book.testimonials.length > 0 && (...)`) already omits the entire section when a book has no testimonials — no filler copy standing in for missing reviews.
- **Sales milestones.** `buildMilestoneText()` (`src/lib/milestoneText.ts`) already does exactly what the brief asks: returns nothing unless a real `milestoneSalesCount` is set, prefixes the sentence with the real month ("In September 2026, …") so the claim is explicitly dated rather than a permanent-sounding figure, and only Shadow Code currently has one (850+ copies, confirmed live in Supabase, dated September 2026 — still accurate and defensible, not stale).
- **Reader-submitted testimonial content itself.** Queried all 14 rows in `authorgaurav_testimonials` directly. Every one already carries a real, traceable source — "Amazon," "Goodreads," "Verified Reader," "Book, Amazon" — consistent with genuine, informally-written reader feedback (typos, emoji, personal asides), not polished marketing copy. Nothing here needed removing.

## Built: the `verified` field and the fields the brief's data model requires

The brief's one concrete technical requirement — "Public rendering should include verified testimonials only," enforced by a `testimonial.verified !== true` validator — had no real field to check. The table only had `quote, name, source, featured, author_reply`. This was a genuine schema gap, not a display gap, so per this engagement's standing rule a DDL change needed your explicit sign-off before touching it; you confirmed adding `verified`, `source_url`, and `date` columns.

Applied migration `add_verification_fields_to_testimonials`:
- `verified boolean not null default true` — defaults to `true` because every row already in this table has already been through your manual approval before being inserted (public submissions land in the separate `authorgaurav_testimonial_submissions` moderation queue first; nothing reaches `authorgaurav_testimonials` without you putting it there). This reflects the real existing process, not a guess.
- `source_url text` (nullable) and `date date` (nullable) — both optional per the brief's own `sourceUrl?` / `date?` notation.
- Tightened the table's public-read RLS policy from "anyone can read every row" to "anyone can read rows where `verified = true`" — this is the actual enforcement of "public rendering should include verified testimonials only," at the database level, not just in application code. Admins keep full read/write access to every row (including any future unverified one) through their own separate policy.

Code changes:
- `Testimonial` type (`src/data/books.ts`) gained `sourceUrl?` and `date?`.
- `fetchBooks`, `fetchFeaturedTestimonials`, and `fetchAllTestimonials` (`src/lib/queries.ts`) now select and map the new columns, and explicitly filter `.eq('verified', true)` in application code too — redundant with the RLS policy, but keeps the rule visible in the query that renders these rather than buried only in a policy.
- New shared `TestimonialMeta` component (`src/components/TestimonialMeta.tsx`) renders name, source (as a real link when `sourceUrl` is set, plain text otherwise), and formatted date — used by both `TestimonialCard` components (`/testimonials` page and the homepage strip) and `BookReview` (book-page reviews), so all three can't drift into different formatting. No visible change today since no existing row has `source_url`/`date` populated yet — purely additive.
- `/admin/testimonials` now has Source URL and Date fields, and a Verified checkbox with inline copy explaining what unchecking it does ("hides it from all public pages immediately"). The testimonial list view flags any unverified row in red so you'd see it at a glance if one ever existed.
- `validate-content.mjs` now fetches testimonials with the public (anon) key and checks every returned row has `verified === true` — since RLS already guarantees the anon key can never see an unverified row, a failure here would mean the RLS policy itself has regressed, making this a real regression guard, not a no-op. It also warns if any testimonial has no `source` at all, matching the brief's "must be traceable" requirement.
